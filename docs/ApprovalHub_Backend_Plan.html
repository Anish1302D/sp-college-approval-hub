§1 — Foundation

Stack decision

The database is not a passive store. It holds the workflow engine, the routing rules, the audit triggers and the security policies. That single fact drives every choice below.

Recommended

Node + Express + pg — no ORM

Plain express for routing, the pg driver for data access, zod for input validation, jsonwebtoken for sessions. JavaScript, not TypeScript — matching the existing frontend.

Why not Prisma

Prisma is the obvious default coming from Supabase, and it is the wrong tool here. Four concrete reasons:

  • It cannot model what you built. fn_record_action, the sanctioned_amount trigger, the RLS policies, the composite foreign keys and the five views have no representation in a Prisma schema. You would reach past Prisma with $queryRaw for the parts that matter most.
  • Prisma Migrate would fight your schema. It wants to own the DDL. Your DDL is hand-authored and already correct. Introspecting it produces a lossy model that drops exactly the constraints and functions worth keeping.
  • RLS needs a session variable per transaction. That pattern is native with a pg client and awkward through Prisma's connection abstraction.
  • Its main benefit is redundant. Prisma sells type safety and migrations. You are writing JavaScript, and you already have a migration workflow.

Without the ORM the API becomes thin, which is the goal: the business logic lives in the database, and the API is transport plus authentication. An approval endpoint is one function call, not fifty lines of orchestration you would have to keep correct.

§2 — The critical piece

The RLS primitive

Everything in the API funnels through one helper. Get this right and security is automatic; get it wrong and either every query returns nothing, or worse, one user sees another's requests.

Three rules the database already enforces, which the API must respect:

  • Connect as app_user. Connecting as postgres silently disables every policy, because superusers bypass RLS.
  • Set app.user_id inside a transaction, with SET LOCAL.
  • With no user set, policies evaluate false and queries return zero rows. It fails closed.

Why SET LOCAL, not SET

Connections come from a pool and are reused. A plain SET persists on the connection after your request finishes, so the next request to borrow that connection inherits the previous user's identity. SET LOCAL is scoped to the transaction and is discarded on commit. This distinction is the whole ballgame.

db.js

import pg from 'pg';

const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL, // app_user, never postgres
  max: 10,
});

// Runs fn inside a transaction that carries the caller's identity, so every
// statement is filtered by the RLS policies. Commits on success, rolls back
// on any throw, and always returns the client to the pool.
export async function withUser(userId, fn) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    // Parameterised: never interpolate a uuid into SQL text.
    await client.query('SELECT set_config($1, $2, true)',
                       ['app.user_id', userId]);
    const result = await fn(client);
    await client.query('COMMIT');
    return result;
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();
  }
}

// For login only — runs with no identity set, so it can only touch
// tables without RLS (users, roles).
export async function anonQuery(text, params) {
  return pool.query(text, params);
}

set_config($1, $2, true) is the parameterised equivalent of SET LOCAL — the third argument means transaction-scoped. Use it rather than string-concatenating a UUID into a SET LOCAL statement.

Every route looks like this

app.get('/api/requests', requireAuth, async (req, res, next) => {
  try {
    const rows = await withUser(req.user.id, async (db) => {
      const { rows } = await db.query(
        'SELECT * FROM v_pending_requests ORDER BY days_pending DESC');
      return rows;
    });
    res.json(rows); // already filtered to what this user may see
  } catch (err) { next(err); }
});

There is no WHERE raised_by = ... anywhere in the API. The policies do it. That is the payoff for having built RLS.

§4 — Identity

Authentication

Password hashes already live in users.password_hash, written by pgcrypto's crypt(). Verification happens in the database, so no bcrypt library is needed.

Login

// crypt(candidate, stored_hash) == stored_hash is bcrypt verification.
// Runs anonymously because RLS is not yet applicable — no user set.
const { rows } = await anonQuery(`
  SELECT u.user_id, u.full_name, u.email,
         ARRAY(SELECT r.code FROM user_roles ur
                JOIN roles r ON r.role_id = ur.role_id
               WHERE ur.user_id = u.user_id) AS roles
    FROM users u
   WHERE u.email = $1
     AND u.is_active
     AND u.password_hash = crypt($2, u.password_hash)`,
  [email, password]);

On success, sign a JWT carrying user_id and the role codes, expiring in a few hours. requireAuth verifies it and populates req.user; withUser(req.user.id, ...) does the rest.

Do not trust roles from the token for authority

Roles in the JWT are fine for showing and hiding UI. They must never be the basis for allowing an approval. Authority is checked inside fn_record_action against stage_approvers — a forged or stale token cannot get past it. Keep it that way.

§6 — Failure

Error handling

The database raises rich, specific errors. The API's job is to turn them into correct HTTP status codes without leaking internals.

Schema change worth making first

fn_record_action currently raises errors as plain messages, so the API would have to match on English text — brittle, and it breaks the moment a message is reworded. Add explicit SQLSTATE codes to each RAISE (RAISE EXCEPTION '...' USING ERRCODE = 'AP001') and map on err.code instead. Class AP is free for application use. This is a small migration and should happen before the API is written against it.

ConditionHTTPResponse
Not an approver at this stage403You are not authorised to act on this request
Request already closed409This request has already been decided
Rejection with no reason422A reason is required to reject
Partial approval with no items422Select which items are approved
Final authority escalating422This is the final stage; it cannot be escalated
CHECK violation (23514)422Field-level message from the constraint name
FK violation (23503)422Referenced record does not exist
Unique violation (23505)409Already exists
RLS returns zero rows on a fetch by id404Not found — never "forbidden", which would confirm it exists

That last row matters. When RLS hides a request, returning 403 tells the caller the record exists and belongs to someone else. Return 404.

§7 — Attachments

File uploads

The schema already decided this: payloads live outside the database, and attachments stores only the pointer.

  • Development and college server: multer writing to a disk directory outside the repo, with storage_path holding the relative key.
  • If it ever moves to cloud: swap the storage adapter for S3 or MinIO. Nothing else changes, because only the adapter knows what a storage_path means.
  • Validate on upload: cap size, allowlist MIME types (PDF, images, Word, Excel), and generate the stored filename yourself. Never use the client's filename as a path — that is how directory traversal happens.
  • Downloads go through the API, never a static route. The handler checks visibility first, then streams. A static folder would let anyone with a URL bypass RLS.
  • Back it up with the database. A pg_dump without the upload directory restores rows pointing at files that no longer exist.
§8 — Integration

The frontend gap

Swapping src/data/mock*.js for API calls will not work as-is. The mock model and the database model disagree in a way that requires real UI changes.

The mismatch

Every mock request has a single amount and one category. The database has a request with many line items, each with its own quantity, unit cost, approved quantity and status. Partial approval — the feature the whole schema was designed around — has nowhere to live in the current UI.

§10 — Delivery

Deployment

Unchanged from the database plan, with the API added as a second service.

  • PostgreSQL as a service on the college server, schema loaded from db/run_all.sql, then migrations from there on. Skip seed/03 or reset every password it creates.
  • API as a Node process kept alive by pm2 on Linux or nssm on Windows, listening on localhost only.
  • Frontend built with npm run build and served as static files by nginx or IIS, which also reverse-proxies /api to the Node process.
  • Secrets in a .env that is never committed — DATABASE_URL and JWT_SECRET at minimum. Commit .env.example with the keys and no values.
  • Backups: nightly pg_dump -Fc plus the upload directory, kept off the same disk. Test a restore before you rely on it.
  • HTTPS before any real login crosses the network. A JWT over plain HTTP on a shared college network is a credential anyone can read.
